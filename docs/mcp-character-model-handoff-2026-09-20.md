## 3. 人物模型的真实现状

### 敌方角色

- `enemy-model.js:7-25` 用 `BoxGeometry` 等基础几何拼出躯干、头、手臂、腿和肩甲；兵种主要靠尺寸、附件和颜色区分。
- `enemy-model.js:97-117` 通过 `userData.parts` 和 `animateEnemy()` 直接旋转手脚、调整预警发光、弱点和隐身表现，不是已接好的骨骼蒙皮角色管线。
- 当前确实有 `MeshStandardMaterial` 金属度/粗糙度升级，但“换 PBR 材质”不等于完成角色造型、拓扑、绑定或动作制作。

### 主角第一人称

- `weapon-models.js` 的 `hand()` 使用球体与胶囊体拼装手套/手指；`createWeapons(camera)` 将持枪视模挂到相机。
- 主角手臂/持枪视模与敌方完整角色是两个独立交付范围，需先确定优先级；本轮没有发现已接入的专用完整主角 GLB。

### 资产管线

- `models/` 当前列出的文件只有 `heavy-cover.glb` 与 `reactor-core.glb`，均为环境资产，不是人物。
- `scripts/build-cover-model.mjs` 使用 Three.js 和 `GLTFExporter` 离线生成真实 GLB；`art.js`、`reactor-arena.js` 已使用 `GLTFLoader`。
- 因而有可复用的静态 GLB 产出/加载基础，但不能称角色骨骼动画、混合、实例化和生命周期已经接好。
- 命令探测确认 Node 和 Python 可用；`blender` 未在当前 Bash PATH 中找到，这不证明系统没有安装 Blender。首批硬表面科幻角色可以采用代码建模加 GLB 导出，不以安装 Blender 为前提。

## 4. 关键接入约束

不能只把一个 GLB 场景挂到旧敌人组中就视为替换完成：

1. `app.js` 多处使用敌人根组的直接子节点、非递归 `intersectObjects(..., false)`，并以 `contact.object.parent === enemy.group` 识别命中归属。导入 GLB 往往增加节点层级，直接替换可能令命中失效。
2. 头部、身体、护甲、核心和机甲腿部依赖 `userData.hitZone`；需要保留稳定的命中代理和归属映射，不随美术细节改变伤害或判定。
3. `enemy-ai.js` 会直接访问 `parts.arms` 与 `parts.accent`；应提供兼容适配层，而非悄悄更改 AI、攻击预警、弱点开合或维修逻辑。
4. GLB 异步加载需要缓存、预加载/占位回退；各实例的受击、隐身和发光状态不能污染共享材质，销毁时也不能误释放仍被其他实例使用的资源。
5. 当前相关文件已有未提交改动。实施前重读并校验版本，新增独立角色资产/适配模块为主，不回退或覆盖已有工作。

## 5. 可以接手的工作与推荐首批

可以接手可在游戏中使用的真实 3D 角色资产，而不只是概念图：造型、材质、关节/基础动画、GLB 导出、Three.js 接入和必要回归。最适合先做与项目现有方向一致的科幻装甲兵或机械人。

电影级写实人脸、精细皮肤/毛发、复杂布料和动作捕捉需要额外素材、工具与反复美术验收，不能把程序硬表面模型承诺成该等级的角色。

建议首批仅做一名“科幻装甲普通守卫”样板，确认效果后再批量派生兵种：

1. 确认是优先敌人士兵、主角第一人称手臂，还是 Boss，以及写实程度与参考图。
2. 延续已记录的写实科幻工业方向，先完善轮廓、人体/机械比例、头盔、分层胸甲、肩甲、膝肘关节和武器挂点；避免只在方块角色上堆装饰。
3. 提供独立预览与可复现构建的 GLB、PBR 材质及必要动作。装甲角色可先用明确关节层级；如果选择真人柔性身体，再确定骨骼蒙皮范围。
4. 确认样板后只替换一个普通兵种；保留碰撞半径、命中区域、伤害、攻击时机、寻路和存档格式。
5. 验收待机/移动/举枪/受击等动作、正侧背轮廓与远距离辨识度、头部/护甲命中、重武器/近战/处决、反复生成销毁和多敌同屏帧耗。三角面数、材质数与同屏数量预算需结合目标设备测量后定，不预先声称已有性能余量。
6. 样板通过后，再派生工程兵、指挥官、重装兵等；第一人称手臂与 Boss 单独排批。

本轮未生成新人物资产，也未开始替换。上述为可执行建议，不是已交付成果。
